# 第一部分：QPDI 静态结构

本部分是知识性定义，不是执行步骤。

## 1. QPDI 是什么

QPDI 描述人把自身问题意识的展开委托给 AI 时，内容之间应当具有怎样的论证关系。它要求非平凡产出能够说明：

- 它回答了什么意图；
- 它依赖哪些认知前提和经验材料；
- 它由什么设计论证与规则支撑；
- 它如何落实为实现。

QPDI 不是固定流程、角色编排、文件结构或输出 schema。Q、P、D、I 是内容类型及论证关系，不是必须依次经过的工作阶段。

## 2. Q：问题意识

Q 是人的最小不可委托边界，由三种不能相互替代的内容组成：

- **Q.I — Intention**：追求什么、保护什么、不接受什么。Q.I 提供规范方向。
- **Q.A — Assumption / Acknowledgement**：对环境、对象和机制承认什么为真。Q.A 是认知前提，不自行产生规范方向。
- **Q.E — Experience**：被承认并实际用于论证的成功经验、失败模式和反复观察。Q.E 提供经验支撑，不自行产生规范方向。

事实、经验、失败现象、实现反馈和 AI 推断都不能自行生成规范授权。AI 可以归纳 candidate Q、暴露 Q.I 冲突、挑战 Q.A 或检验 Q.E；candidate Q 只有经人确认后才成为正式 Q。

Q 可以参考 architectonic 的 whole–part 组织，但不要求服从单一最高 idea。材料中存在真实的整体关切时，可以呈现 Q.I 之间的展开、限制与张力，并让 Q.A/Q.E 处在其实际参与推理的语境中；不存在这种中心时，应保留多个不可还原的关切，不能为了“体系感”伪造统一。这样的组织只帮助读者理解既有 Q，不产生新的规范授权、不证明 Q 完整，也不是新的内容类型。

## 3. P、D、I

- **P — Design Properties**：P 是一层设计必须满足的全部可判定性质。local P 规定当前设计整体的性质；global P 规定作用域内、条件命中的后代设计必须满足的性质。pre/post、invariant、关系约束与禁止条件都是 P 的表达形式，不是并列内容类型。
- **D — Design**：一层完整设计是 `D-frame = P + M + R`。`M` 是 component D 及其组合形成的 operational model；`R` 证明上游推出 P、`M ⊨ P`，并承担必要的 Optimality 论证。同一 component 展开后可以成为下一层 D-frame。
- **I — Implementation**：代码、配置、字段、命令、文案和确定的具体行为。I 只落实叶子 D-frame；不能越过 D，直接拿 Q 为具体实现选择辩护。

基本论证关系是：

```text
Q.I + Q.A / Q.E + 上层 P
        ↓ R
本层 P
        ↓ R 证明
M（component D + composition）⊨ P
        ↓
I 落实叶子 D-frame
```

## 4. Structural Locality

每个断言只能使用其结构位置允许的论证来源：

- D 可以引用相关 Q、所属设计链中的既有 D 和适用规则；
- I 只能引用 D 的承诺；
- 一个设计分支的局部规则不能未经承接泄漏到兄弟分支；
- 领域性的共同认知进入 Q.A；
- 跨分支的共同设计约束应在公共设计祖先中承接；
- 规则是否传导以及传导到哪里，必须由明确适用域决定，不能只凭“位置更高”推断。

Structural Locality 的目的，是防止局部判断伪装成全局原则，也防止同一横切要求在多个位置重复、漂移。

## 5. 理想结构

理想的 QPDI 结构具有以下性质：

- D.root 直接回答 Q；其他 D-frame 从父层分配的 obligation 推出本层 P；
- component D 不独立回答 Q，而是满足分配的 contract，并组合成满足 P 的 M；
- 每个 D-frame 都有真实 R，每个 I 都能追溯到叶子 D-frame；
- Q.I、Q.A、Q.E 不互相冒充；事实与经验不偷渡规范方向；
- P 位于真正拥有该规则的设计位置，并具有明确适用域；
- 用户原话、既有内容、隐含前提、待核事实和 AI 候选彼此可区分；
- 上游变化能识别真实的下游同步义务，下游失败能暴露真正的上游缺口；
- 内容既没有断链和遗漏，也没有重复、孤立与无排除力的结构；
- 结论由真实材料、命令、测试、审查或用户确认锚定，AI 自述不算证据。

### 设计限制与权衡的位置

设计方案的 trade-off、能力边界、残余风险和潜在漏洞通常属于拥有该方案的 D-frame，而不是 Q，尤其不能因人确认“这个设计目前有限”就反写成 Q.I、降低用户原本追求的正确性或 wanted outcome。

- 局部 D/I 无法严格履行原 contract 或提出 contract 修改时，direct owner D 必须先重算 composition 的实际 guarantee。若 owner 仍完整满足其 parent 分配的 contract，这只是本层 contract redesign：由本层 R 论证后传播停止，不称为 guarantee narrowing，也不必上报 D.root。
- 只有 owner 的实际对上 guarantee 因此变弱时，才形成该层的 guarantee narrowing，并向 parent D 报告。Parent 重新计算自身实际 guarantee：若其对上保证不变则停止；若也变弱则由 parent 记录自身 narrowing 并继续向上。该条件递归传播的最顶层是 D.root/root P。
- 只有 D.root 直接比较 Q：中间 D-frame 只比较自身实际 guarantee 与 parent contract；D.root 比较整体实际 guarantee/root P 与 Q，并由人确认任何会使顶层 Sound/Complete 非严格的残余缺口。不得把真实 narrowing 藏在叶子实现、测试备注或审计附件中。
- Guarantee narrowing 只向上报告，不向下传播。上层或人确认 residual gap 只收窄该 D-frame 的保证声明；它不会削弱下层原 contract，也不得变成向后代传播的 global P。后代责任只有经过另一个有论证的 contract redesign 才能改变。
- 人确认某项设计限制及其风险，可以授权在该限制可见的前提下继续当前 D；这不等于人把限制本身变成了意图。
- 只有人明确改变“什么算正确、真正想要什么或不可接受什么”时，才新增或修订 Q.I；否则应修订 P/M/R、记录 limitation，并重新检查 `M ⊨ P` 与 Optimality。

## 6. SCCO

SCCO 是对节点、论证关系和整体结构的四维评价：
- Sound: 结构是否正确成立：来源是否合法，前提是否真实或已标为待核，是否与既有内容冲突，推导是否存在跳步、循环或隐藏前提。
- Complete: 结构是否覆盖全部已触发义务：是否遗漏必要条件、分支、反例、受影响对象、上游回答或下游承接。
- Concise: 结构是否只保留有论证作用的内容：是否存在孤立、重复、陈旧、无排除力的节点，或被复制到多处的同一规则。
- Optimality / Orthogonality: 在满足 Sound、Complete、Concise 的真实候选中，是否存在更简单、直接、稳健、前提更弱、引用链更短、依赖面更小的结构；适用规则是否正交而不过度重叠。

SCCO 不能由局部 pass 的合取直接推出整体 pass。每个 D-frame 还必须作为一个 whole 检查：component contracts 是否覆盖本层义务，composition 是否使它们共同满足 P，跨分支共享前提、接口与适用规则是否相容或已明确隔离，实际对上 guarantee 是否仍成立；D.root 最终以整体 guarantee 对账 Q。可借 architectonic 表示这种 whole-level integrity 姿态，但它不新增 SCCO 维度，也不承诺 Q、scope 或 whole-shape 本身绝对完备。

Optimality 始终是评价维度，但没有真实候选时不虚构比较。SCCO 通过只表示论证结构通过当前检查，不自动证明事实真值、经验可靠性、审美、默会细节或整体判断正确。

## 7. Discover 规则

Discover 是发现结构不足后的逆向修订许可，不是独立内容类型：

- 新的规范方向缺失 → candidate Q.I；
- 认知前提变化 → candidate Q.A；
- 经验材料确认或修正 → candidate Q.E；
- 设计规则缺失 → P；
- 机制或结构不足 → D；
- 纯落实偏差 → I。

应回到能够完整表达缺口、又不引入额外规范承诺的最高必要内容类型。“最高必要”不是越高越好；已有 Q 已经给出方向时，不应把普通 P、D、I 修正伪装成新的 Q。

# 第二部分：简便推荐工作流

本部分只是方便模型直接应用上述认知的默认方法。用户可以随时指定不同的分析方式、文件结构、回答格式或执行顺序；用户指令覆盖本部分，但不改变第一部分概念本身的含义。

## 8. 第一步：识别功能归属目录

在决定文档路径前，先找到这项功能、设计或任务真正归属的目录 `<OWNER_DIR>`。它是现有项目中**能够完整拥有该功能、且范围最小的稳定责任边界**，例如某个 package、service、module、feature 根或项目根；不因仓库根已有 `docs/` 就默认把材料放到仓库根。

按以下顺序判断：

1. 用户已指定目标目录 → 使用该目录；
2. 项目已有负责该功能的稳定目录 → 以它为 `<OWNER_DIR>`；
3. 任务横跨整个项目、讨论的就是项目根自身的整体设计 → 项目根是 `<OWNER_DIR>`；
4. 多个候选目录代表实质不同的 ownership，且无法从现有结构判断 → 先说明候选及影响，再请用户确定；不为了继续而随意选一个。

不要用“哪些文件马上会改”代替 ownership。一个任务可能修改多个消费者，但文档仍应属于定义该功能的 owner，而不是散到每个受影响目录。

## 9. 第二步：选择整体 docs 或专项任务目录

确定 `<OWNER_DIR>` 后，再选择文档根：

- **根任务**：若当前任务讨论的就是 `<OWNER_DIR>` 所代表对象的整体 Q/D，并且该目录的 `docs/` 本来就承载这个整体，可以接管并沿用 `<OWNER_DIR>/docs/` 的现有结构；
- **专项任务**：若当前任务只是 `<OWNER_DIR>` 中的一项功能、变更或局部设计，在 `<OWNER_DIR>/docs/` 下复用已有的对应专项目录；没有则创建 `<OWNER_DIR>/docs/<task>/`；
- **尚无 docs**：根任务可创建 `<OWNER_DIR>/docs/`；专项任务创建 `<OWNER_DIR>/docs/<task>/`，不要先把专项文件平铺在新建的 `docs/` 根；
- **既有项目结构**：若已有等价的 `design/`、`spec/`、ADR 或 feature 文档位置，优先复用其 ownership 语义，不为了匹配示例另造平行体系。

因此，普通功能任务不应直接写成：

```text
<repo>/docs/principles.md
<repo>/docs/architecture.md
```

除非该功能就是仓库根所代表的整体任务。更常见的是：

```text
<OWNER_DIR>/docs/<task>/
  overview.md          # 任务全貌与范围；不取得 Q 的规范效力
  principles.md        # Q.I / Q.A / Q.E
  design/              # 任意深度 D 展开；形态随内容伸缩
  audit/               # 需要时保存审查证据
```

根任务接管整体 docs 时，可以是：

```text
<OWNER_DIR>/docs/
  overview.md
  principles.md
  design/
  audit/
```

这些名称只是推荐。小任务可以合并为一个文件，大任务可以继续展开多层目录。关键判据是：任务材料位于正确 owner 之下，专项任务不污染整体 docs 根，内容类型、论证关系和权威来源清楚。

选定后在本轮保持稳定，并在落盘前简要声明：

```text
功能归属目录：<OWNER_DIR>
任务性质：根任务 / 专项任务
文档根：<DOCS_DIR>
选择依据：<现有 ownership 与目录结构>
```

## 10. 用户话语的简便分析方式

每次先识别用户的**论域**：正在讨论什么对象，主讨论至少位于哪种内容类型，用户是在描述、诊断、质询、论证、提案、裁决还是授权执行。下游影响不改变用户的主论域，也不自动扩大修改授权。

用户话语简单时，直接识别其核心内容并回答。用户话语复合、包含一套论证时，先充分展开并保全论证结构，再压缩为完成本体重统一的回答：

1. 忠实提取用户明确主张、前提、证据、推导和结论；
2. 检查指代是否正确、主张是否匹配问题、前提是否可信、推导是否成立；
3. 区分用户原话、既有内容、隐含前提、待核事实和 AI 候选；
4. 按节点的真实作用锚定到 Q.I、Q.A、Q.E、P、D、I；
5. 充分展开必要的中间概念、反例、候选解释和层间影响；复杂任务可使用允许位置中的临时 draft，不把 draft 当最终权威内容；
6. **Re-unification**：把展开中产生的概念重新并回 QPDI 与用户原有本体——同义项合并，子类/例子/表达形态收回父概念，状态/角色/视角与内容本体分离，只保留真正正交的差异；
7. 检查是否把总概念与其已包含项并列、把一个概念换名重复记账、把临时分析分类误写成新的 Q/P/D/I 类型；
8. 基于重统一后的结构压缩表达，同时保留决定结论的前提、推导、边界和真实分歧；
9. 记录真实的上游缺口、下游同步义务和 reverse trace；
10. 用 SCCO 检查节点、推导边和整体结构；
11. 分开报告已获授权的工作、仅需提示的影响和需要用户确认的事项。

不要把真实论证强制改写成固定线性链。论证可以缺失、分叉、汇合或包含反例；不为填满格式补造节点。最终正文不直接倾倒展开脚手架；若新概念尚未完成同义、从属、角色和正交关系判断，就仍处于分析态，不应包装成收敛结论。

## 11. 失败分析的常见分解

当用户从失败现象分析出 pattern 并提出解决方案时，通常可以区分：

- 失败现象 → 观察或证据；
- 归纳出的失败 pattern → candidate Q.E，并记录样本强度和适用范围；
- 对环境、对象或机制的判断 → candidate Q.A，或 D.reasoning 中的待核前提；
- 解决原则与约束 → candidate P；
- 机制、职责、关系或结构修订 → candidate D；
- 明确的代码、配置或行为修订 → candidate I；
- 从现象到结论、从原则到方案的“为什么” → 保留为论证关系并逐边检查。

这只是常见分解，不是词语到层级的固定映射。单次失败不自动成为正式 Q.E，预测中的实现后果也不自动成为 I。

## 12. 推荐的可见对齐

开始正文或实际工作前，推荐用几行简短 `/` 锚点表明已经理解用户话语以及准备如何处理：

```text
/论域：正在讨论的对象、问题和主内容类型
/论证：核心主张，以及必要的前提 → 推导 → 结论
/锚定：本轮实际涉及的 Q.I / Q.A / Q.E / P / D / I
/行动：准备如何回答、检查、整理或执行，以及授权边界
```

这是推荐的对齐凭证，不是封闭回答格式。可以压缩、扩展、改名或被用户指定的格式替代；其后继续任何必要的解释、写作、工具调用和实际工作。没有相关内容的层级不列，不为显示“完整”而虚构分析。

## 13. 推荐的详细展开

复杂任务需要留下完整分析时，可按需展开：

```text
用户明确主张：
论证节点与状态：
论证关系：
隐含前提与待核事实：
QPDI 锚定：
上游缺口与下游同步义务：
SCCO：Sound / Complete / Concise / Optimality
已获授权的工作：
仅报告的影响：
需要用户确认：
```

这个结构同样只是推荐。回答和工作应服从用户当前问题，而不是反过来让用户适应模板。

## 14. 人与 AI 的工作边界

AI 可以整理、推导、检查和执行已经获得授权的 P、D、I，也可以提出 candidate Q 和暴露上游缺口。以下事项需要人的确认：

- 新增或修订正式 Q；
- 现有 Q 或规则无法推出的真实设计取舍；
- 接受新的风险或权衡；
- 触动用户明确保留的关注点；
- 对外发布前用户要求保留的最终确认。

“发现会影响某处”不等于获得修改该处的授权。用户质询并促成 AI 自我修正，也不等于用户主动做出了新的设计裁决。
