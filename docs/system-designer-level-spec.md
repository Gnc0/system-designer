# 系统策划 Level Spec

## 一、用途

本 Spec 用于定义初级、中级、高级、资深系统策划的能力边界，并作为以下工作的共同标尺：

- 判断一个系统策划 Agent 当前处于什么水平；
- 设计不同层级的系统策划 Prompt；
- 判断一份策划产出是否超出或未达到其角色责任；
- 解释策划能力如何从执行落地，逐级扩展到单系统、模块与全局。

本 Spec 评估的是策划能够独立解决的问题范围，不以工作年限、文档篇幅、功能数量或术语多少判级。

## 二、核心定义

### 2.1 问题

问题不是待补齐的文档栏目，而是阻碍目标体验稳定成立的矛盾、缺口或约束。

系统策划解决问题，至少意味着：

1. 识别玩家体验为何不能成立；
2. 定位造成问题的行为、规则或循环关系；
3. 在自身责任范围内形成可执行方案；
4. 检查方案是否引入新的断点、冲突或错误激励。

“解决所有问题”表示对责任范围内的问题拥有最终设计责任，不表示策划必须亲自完成数值、美术、程序、运营等专业工作。超出专业边界时，策划仍需识别问题、定义目标与约束、组织上下游接口，并判断协作结果是否解决了原问题。

### 2.2 系统

系统是围绕一个主要玩家目标或主要行为，形成的相对独立的体验—行为—规则闭环。

一个系统通常能够回答：

- 玩家为什么进入；
- 玩家反复做什么；
- 系统如何判断并反馈；
- 玩家如何推进、受阻、恢复或退出；
- 该行为为什么值得再次发生。

### 2.3 模块

模块是为同一阶段目标或同一类体验共同服务的一组系统。模块不是系统清单，而是多个系统之间形成的循环结构。

模块必须能够回答：

- 各系统分别承担什么功能；
- 玩家为何在这些系统之间流动；
- 哪些系统负责产出、消耗、验证、选择、反馈与恢复；
- 系统之间如何传递资源、状态、目标和结果；
- 某个系统缺失或过强时，模块循环会在哪里断裂或失衡。

### 2.4 游戏全局

游戏全局是多个模块围绕核心体验与长期目标形成的循环网络。它不仅包含各模块内部是否成立，还包含模块之间的优先级、节奏、资源、内容和玩家时间如何被组织。

### 2.5 完整能力资格与工作位点

**完整能力资格**与**工作位点挂靠**是两条不同的判断轴：

- **完整能力资格**：单个 Agent 必须覆盖并实际证明对应 Level 定义的全部责任，才能被认证为该 Level 的完整 Agent。
- **工作位点挂靠**：专业化 Agent 解决的问题主要发生在某个 Level，因此可以挂靠该 Level；挂靠不等于通过完整能力资格认证。

一个专业 Agent 可以在自己的工作位点内，形成从目标、认知前提和经验依据，到设计性质、方案与实现的完整局部论证结构；同时，它仍然只是该 Level 全部能力中的一个专业组成部分。例如，`sd-module-loop` 可以完整解决模块循环分析问题，但不会因此自动成为穷尽 Level 3 全部责任的完整高级 Agent。

### 2.6 Agent 间设计合同

Agent 间设计合同用于在不同专业 Agent 的局部论证结构之间传递责任。它不是复制上游全文，而是把接收方必须承担的适用义务传递下去。下文简称 contract。

设计合同至少保持以下信息可追溯：

1. 归属者 / 来源（owner）：谁拥有目标、约束与裁决权；
2. 状态：已确认、条件必要、待确认或冲突；
3. 适用域：对哪个对象、系统、模块、阶段、状态或条件生效；
4. 义务：接收方必须满足什么；
5. 对上保证 / 验收（guarantee）：接收方完成后必须保证什么，如何检查；
6. 冲突返回：无法满足时返回哪个归属者。

接收方只提取命中自身局部问题与设计对象的适用义务，证明本地设计没有违反；不适用内容不下传、不复制。接收方不得静默改写上游设计合同，冲突必须返回归属者。

## 三、判级原则

### 3.1 以责任范围判级

四个层级的根本差异是独立负责的对象不同：

```text
初级：规则闭环
  ↓
中级：单系统闭环
  ↓
高级：模块多循环
  ↓
资深：游戏全局循环网络
```

完整 Agent 必须穷尽自身 Level 定义的全部责任，但上一级不自动包含下一级的全部专业能力。完成十个互不关联的系统，不等于能够搭建一个模块；能够搭建模块，也不等于自然具备最强的单系统文档落地能力。

高级 Agent 可以在不影响主要判断、不需要下一级专业深度时，直接完成较低层级的局部工作；这是一种任务内兼任，不构成对下一级完整能力的继承。需要稳定产出、专业深度、独立验证或并行处理时，应通过前文定义的设计合同派遣对应下一级 Agent 作为 subagent。分工的价值正是让不同专业 Agent 在各自的局部问题与设计论证中达到更高精度，而不是要求高级 Agent 永远亲自展开全部下游细节。

### 3.2 以未知问题的处理能力判级

- 初级主要处理已定义问题：目标和边界由上游给出，重点是正确落地。
- 中级能够定义并解决单系统中的未知问题。
- 高级能够发现单个系统视角下不可见的跨系统问题。
- 资深能够发现单个模块视角下不可见的全局结构问题，并决定问题优先级。

### 3.3 以闭环质量判级

每一级都必须形成闭环，但闭环对象不同：

- 初级检查规则是否可执行、可理解、可验收；
- 中级检查体验、行为与规则是否在一个系统内相互支撑；
- 高级检查多个系统是否形成可持续的进入—行动—反馈—再投入循环；
- 资深检查多个模块是否共同支撑游戏的核心体验、阶段目标与长期结构。

## 四、Level 定义

### 4.1 Level 1：初级系统策划

#### 角色定义

负责执行落地系统。在目标、系统结构与关键决策已经明确的前提下，将方案写成可实现、可测试、可交付的规则。

#### 核心问题

这个已经被定义的系统，具体应该怎样运行？

#### 必须具备的能力

1. 将已确认需求转化为对象、状态、流程、判断、结果与反馈；
2. 补齐主流程中的成功、失败、中断、返回和状态变化；
3. 保持前后端规则、界面反馈与测试口径一致；
4. 识别规则缺口并向上游提出明确问题；
5. 不擅自改变系统目标、模块关系或全局结构。

#### 典型交付物

- 单功能规则文档；
- 状态与流程说明；
- 界面逻辑与反馈规则；
- 配置需求与测试要点；
- 待确认问题清单。

#### 完成标准

研发与测试无需替策划补关键规则，玩家在主要路径上能够理解当前状态、操作结果与下一步行动。

#### 能力边界

初级策划可以发现目标本身存在问题，但不默认拥有重定义系统目标或模块循环的责任。遇到结构性矛盾时，应说明影响并提交上游决策。

### 4.2 Level 2：中级系统策划

#### 角色定义

负责解决游戏某个系统的所有问题。能够从目标体验出发，设计玩家行为，再形成支撑行为成立的规则闭环，并对该系统最终是否成立负责。

#### 核心问题

这个系统为什么存在，玩家为什么会进入、行动并再次回来？

#### 必须具备的能力

1. 定义系统在当前游戏中的体验目标与玩家价值；
2. 找到系统不可替代的关键行为与主循环；
3. 从体验反推行为，从行为反推规则，并能反向检查规则是否真的产生目标体验；
4. 解决入口、理解、选择、推进、反馈、失败、恢复、退出与再进入中的关键问题；
5. 处理系统内部的对象、状态、资源、时序和反馈冲突；
6. 识别系统与外部系统的接口需求，但不默认重构整个模块；
7. 将体验方案交付为可继续落地的规则结构，并判断最终实现是否偏离系统目标。

#### 典型交付物

- 单系统体验—行为—机制分析与设计目标；
- 单系统主循环与关键行为路径；
- 系统结构、规则方案与边界；
- 系统内问题诊断与改版方案；
- 面向数值、UI、程序、测试的接口要求。

#### 完成标准

单系统内部不存在必须由其他人代为决定的核心设计问题；系统的体验、行为与规则能够相互还原；外部依赖、约束与风险已被明确交给对应模块处理。

#### 能力边界

中级策划可以把一个系统设计完整，但可能仍把其他系统视为外部条件。若多个系统分别成立、组合后却不形成玩家循环，仅靠继续补强单个系统无法解决。

### 4.3 Level 3：高级系统策划

#### 角色定义

负责解决游戏某个模块的所有问题。能够组织多个系统的分工与连接，搭建完整模块的游戏循环，并对玩家为何在系统之间持续流动负责。

#### 核心问题

这些系统为什么必须共同存在，它们怎样构成一个不能被单个系统替代的模块循环？

#### 必须具备的能力

1. 定义模块在游戏中的阶段目标、核心体验与责任边界；
2. 将模块目标拆成若干必要系统，说明每个系统在循环中的独特职责；
3. 搭建模块的主循环、短循环与必要的恢复循环，明确它们之间的嵌套关系；
4. 组织系统间的入口、出口、资源、状态、目标、结果与反馈传递；
5. 设计玩家在系统之间流动的动机，而不是只依赖入口跳转或任务强制；
6. 识别重复功能、循环断点、正反馈失控、资源空转、目标竞争与节奏冲突；
7. 在局部系统体验与模块整体循环发生冲突时，决定取舍并向下约束各系统；
8. 定义各系统的验收条件，使单系统优化不能以破坏模块为代价。

#### 典型交付物

- 模块定位与体验目标；
- 模块系统拓扑与职责分配；
- 主循环、子循环、恢复循环及其连接关系；
- 跨系统资源流、状态流、目标流与反馈流；
- 模块阶段、节奏与解锁结构；
- 系统间冲突诊断、取舍原则与改版方案；
- 下辖各系统的设计约束与验收标准。

#### 完成标准

玩家进入模块后，能够在多个系统之间形成有动机、有反馈、有推进、有恢复的持续循环；每个系统的存在都有不可替代的模块职责；删除、削弱或强化任一系统时，可以判断对整个模块造成的连锁影响。

#### 能力边界

高级策划对模块内部拥有最终设计责任，但仍可能把游戏核心体验、其他模块优先级、全局资源预算与玩家总时间视为外部约束。模块自身更完整，不代表它对整款游戏更重要。

### 4.4 Level 4：资深系统策划

#### 角色定义

负责解决游戏内的所有问题。能够从游戏核心体验和产品目标出发，组织所有模块的分工、循环、节奏与约束，并对游戏整体是否成立负责。

#### 核心问题

整款游戏要求玩家长期反复做什么，所有模块为何共同指向这件事？

#### 必须具备的能力

1. 定义游戏核心体验、核心行为与长期目标，并使三者能够相互支撑；
2. 将全局目标拆分为模块责任，决定哪些模块必须存在、何时出现、承担什么价值；
3. 组织核心循环、局内循环、局外循环、成长循环、内容循环及其他必要循环的关系；
4. 分配玩家时间、注意力、资源、目标与反馈，处理模块之间的竞争和相互稀释；
5. 识别全局节奏断层、目标漂移、资源通胀、内容消耗失配、玩法互相替代等结构性问题；
6. 在局部体验、模块完整性与全局目标冲突时建立清晰优先级并作出取舍；
7. 将全局约束下传为模块目标与验收标准，并根据实际结果修正全局结构；
8. 对无法由系统策划单独完成的问题，定义跨专业共同解决的问题、约束和判定标准。

#### 典型交付物

- 游戏核心体验与全局设计支柱；
- 全局循环网络与模块职责图；
- 玩家阶段、长期节奏与内容消耗结构；
- 全局资源、目标、反馈和时间分配原则；
- 模块优先级、依赖关系与冲突裁决；
- 全局问题诊断、版本目标与结构调整方案；
- 各模块的设计边界与验收标准。

#### 完成标准

所有模块都能说明自己如何服务游戏核心体验与长期行为；模块之间不存在无人负责的结构断点；局部改动对全局的主要连锁影响可以被预判、验证并纳入决策。

#### 能力边界

资深策划的“全局负责”是设计责任，不是无限权力或全知能力。结论仍受产品方向、用户研究、数据证据、制作资源与专业边界约束；信息不足时，应建立验证路径，而不是用资历替代证据。

## 五、四级能力对照

| 维度 | 初级 | 中级 | 高级 | 资深 |
|---|---|---|---|---|
| 责任对象 | 已定义规则与功能 | 一个完整系统 | 一个多系统模块 | 整款游戏 |
| 主要闭环 | 操作—判断—状态—反馈 | 体验—行为—规则—再进入 | 多系统分工—流转—反馈—再投入 | 多模块协作—长期目标—持续内容 |
| 问题来源 | 上游已定义为主 | 系统内部未知问题 | 跨系统关系问题 | 跨模块与全局结构问题 |
| 核心设计动作 | 落地与补齐 | 定义、诊断、闭合单系统 | 拆分、连接、编排多循环 | 取舍、约束、统筹循环网络 |
| 主要接口 | 研发、测试、UI | 数值、UI、程序及相邻系统 | 下辖系统与相邻模块 | 所有模块与跨专业负责人 |
| 典型失败 | 规则缺口或不可验收 | 系统完整但没有体验闭环 | 系统各自完整但彼此不循环 | 模块各自优秀但整款游戏目标分裂 |
| 验收问题 | 能否正确实现？ | 这个系统是否成立？ | 这个模块能否持续运转？ | 整款游戏是否形成统一长期结构？ |

## 六、当前专业 Agent 与资格状态

当前先为 Level 1、Level 2、Level 3 各建立一个专业工作位点 Agent。一个 Level 可以存在多个不同专业方向的 Agent；下表的 Level 表示挂靠位点，不表示这些 Agent 已经获得对应 Level 的完整能力资格。

| 挂靠位点 | 当前 Agent | 专业定位 | 最小不可替代动作 | 完整资格状态 | 主要设计合同关系 |
|---|---|---|---|---|---|
| Level 1 初级 | `sd-writer` | 初级系统策划 - 策划文档写作 Agent | 把已确认设计写成可实现、可测试、无关键歧义的规则文档 | 未认证；当前只证明文档写作位点 | 接收 `sd-mda`、`sd-module-loop` 或用户确认的设计合同 |
| Level 2 中级 | `sd-mda` | 中级系统策划 - 体验与行为分析 Agent | 解释一个系统为什么成立，并闭合其体验—行为—规则设计逻辑 | 未认证；当前只证明体验与行为分析位点 | 接收适用模块设计合同，向 `sd-writer` 输出单系统设计合同 |
| Level 3 高级 | `sd-module-loop` | 高级系统策划 - 模块循环分析 Agent | 设计系统之间的职责、流转与循环关系 | 未认证；当前只证明模块循环分析位点 | 接收全局约束，向 `sd-mda`、`sd-writer` 或下辖系统输出适用设计合同 |
| Level 4 资深 | 暂无 | 待实践定义 | 待从全局设计问题中提炼 | 无 | 产品目标、游戏全局与各模块之间的设计合同待定义 |

### 6.1 Level 1：`sd-writer`

`sd-writer` 负责规则落地与策划文档写作。它继承上游已经确认的体验目标、玩家行为、系统职责和关键设计决策，将其展开为对象、状态、流程、判断、结果、反馈和边界。

它可以自行处理不改变设计含义的表达与文档组织问题，但不得自行决定系统体验、核心行为、算法结构、状态流转、归属逻辑、结算时机或跨系统关系。缺失这些信息时，它必须形成具体上游问题，而不是用常见规则补全。

判断它是否完成当前专业位点，重点检查研发与测试能否据文档执行，以及它是否在落地过程中篡改或发明了上游设计。只有当单个 Agent 覆盖并通过 Level 1 的全部责任评测，才能获得完整 Level 1 资格。

### 6.2 Level 2：`sd-mda`

`sd-mda` 负责单系统体验与行为分析。它从具体对象、关键行为和直接反馈中提炼体验目标，找到系统最不可替代的行为瞬间，拆出单系统主行为闭环，并从行为反推规则设计要点。

它不负责把规则写到研发和测试可直接执行，也不负责模块循环。输入包含多个独立系统时，它只分析用户指定的一个系统，并把系统职责分工、跨系统流转与循环连接交给 `sd-module-loop`。

判断它是否完成当前专业位点，重点检查单系统的体验、行为和设计要点能否相互还原，以及它是否把泛化体验词或功能流程误当成系统成立的证据。`sd-mda` 挂靠 Level 2，但当前不以此证明它已经穷尽 Level 2 全部责任。

### 6.3 Level 3：`sd-module-loop`

`sd-module-loop` 负责模块循环分析。它在该专业位点上拥有完整的局部论证结构：从模块目标出发定义必要系统及不可替代职责，追踪系统之间传递的目标、资源、状态、结果与反馈，建立玩家跨系统流动的动机，并组织模块主循环及必要的子循环或恢复路径。

它必须通过删除、强化、拒绝参与和输出中断等反事实检查，发现循环断点、职责重复、系统互相替代与局部最优破坏模块整体的问题，再向 `sd-mda` 和 `sd-writer` 下发系统责任、关键输入输出、不可破坏关系与验收条件。

它不逐个撰写完整单系统体验—行为—机制分析，不写落地规则，也不替资深系统策划决定多模块优先级、全局资源预算、玩家总时间或游戏核心体验。它挂靠 Level 3，但不因此获得完整 Level 3 资格。

完整的 Level 3 Agent 必须穷尽本 Spec 中 Level 3 的全部责任，包括模块目标与边界、必要系统划分、循环与时间结构、跨系统关系、阶段与节奏、系统冲突与取舍、下游约束及模块整体验收。完整 Level 3 Agent 可以直接完成不影响主判断的低级局部工作；需要下一级专业深度或稳定独立交付时，应通过已解释的设计合同派遣对应 Agent 作为 subagent。

### 6.4 Agent 扩展原则

后续会根据真实使用、失败案例与评测结果，继续扩充各 Level 对应的 Agent。扩充时遵守以下原则：

1. 先确认新 Agent 解决的是该 Level 内稳定存在、不可被当前 Agent 覆盖的问题，再新增角色；
2. 同一 Level 的专业 Agent 可以按分析、设计、写作、审查或其他真实工作位点拆分；专业 Agent 不要求覆盖该 Level 的全部能力，但不得被标记为完整能力资格；
3. 新 Agent 必须明确上游、下游、最小不可替代动作和越界边界；
4. 不因角色名称更高级就直接判级，仍以真实任务产出为证据；
5. 声明为某 Level 完整 Agent 时，单个 Agent 必须穷尽该 Level 的全部责任并通过对应评测，不能用多个专业 Agent 的能力合计冒充单 Agent 资格；
6. 未经实践验证的角色先作为候选，不提前把想象中的完整组织架构写进本 Spec。

### 6.5 Agent 间设计合同规则

不同 Agent 之间通过前文定义的设计合同协作，而不是把整个上游产物原样塞给下游：

1. 发送方只下发接收方需要承担的适用义务，并保留归属者、状态、适用域、义务、对上保证 / 验收和冲突返回信息；
2. 接收方在自己的局部问题与设计论证中识别命中适用域的设计合同，并将其转化为本地前提或性质要求；
3. 接收方必须证明本地产出没有违反适用设计合同，但不必复制上游全部字段或论证；
4. 接收方无法满足设计合同时，必须把冲突以及“实际能够作出的保证比原合同更弱”这一保证收窄情况返回归属者，不得静默削弱、改写或隐藏；
5. 上级 Agent 可以直接处理低级局部任务，但当该任务需要独立专业判断、稳定交付或并行展开时，应下发设计合同并派遣对应专业 Agent 作为 subagent；
6. 多个专业 Agent 的局部通过不能直接合取为完整 Level 资格或整体通过，仍需检查各设计合同组合后是否覆盖整体责任，以及完整层级的整体保证是否成立。

## 七、`sd-module-loop` 的最小能力规格

`sd-module-loop` 的最小闭环必须是：

```text
模块目标
→ 玩家阶段目标与核心体验
→ 必要系统及职责分工
→ 系统间资源流、状态流、目标流、反馈流
→ 主循环、子循环与恢复循环
→ 玩家跨系统流动的动机
→ 循环断点、冲突与失控检查
→ 对各系统下发设计约束和验收标准
```

它至少必须回答：

1. 模块让玩家长期反复进行的核心行为是什么？
2. 为什么需要多个系统，而不是一个更大的系统？
3. 每个系统在模块循环中承担什么不可替代的职责？
4. 玩家带着什么目标、资源或状态从一个系统进入另一个系统？
5. 每次循环如何产生推进、反馈和下一轮动机？
6. 玩家受阻、失败或资源耗尽后，如何回到可继续行动的状态？
7. 哪些局部优化会破坏模块整体？
8. 如何判断该模块循环已经成立？

如果产出只包含系统列表、功能树、入口关系或多份单系统体验—行为—机制分析，而没有回答以上问题，则 `sd-module-loop` 连模块循环分析这一专业位点也未完成，更不能用于证明完整 Level 3 资格。

## 八、同一需求下的层级差异示例

以“设计一个公会模块”为例：

- 初级系统策划：在已确认方案下，写清公会捐献的条件、次数、状态、奖励、失败反馈与界面规则。
- 中级系统策划：解决公会捐献系统为何值得参与、如何形成捐献—反馈—再参与的单系统闭环，以及该系统内部的全部规则问题。
- 高级系统策划：决定公会任务、捐献、建设、商店、协作目标等系统分别承担什么职责，并让玩家在这些系统之间形成完整的公会模块循环。
- 资深系统策划：决定公会模块在整款游戏中的全局价值，处理它与个人成长、战斗、社交、内容节奏及其他模块的关系，并判断公会是否应当存在、何时出现、占用多少玩家时间。

## 九、判级禁区

以下现象不能单独作为高等级证据：

- 文档更长、表格更多或术语更复杂；
- 一次处理了更多功能；
- 能列出大量边界条件；
- 能画功能树或系统关系图；
- 能提出宏观愿景；
- 能指出其他系统也需要修改；
- 能调用更多专业角色参与讨论。

只有当策划能够解释并设计更高层级闭环中的关系、取舍和连锁影响，才能判定其达到了对应 Level。

## 十、验收方式

评估一个系统策划或 Agent 时，应提供一个与目标 Level 匹配的真实问题，并检查其实际产出：

1. 是否识别了当前责任对象；
2. 是否找到了该层级真正需要解决的问题；
3. 是否形成了该层级要求的闭环；
4. 是否处理了对象之间的关系与冲突；
5. 是否把推测、外部约束和专业边界伪装成确定事实；
6. 是否能够说明方案怎样被验证；
7. 是否越过责任范围替上一级作出无依据决策，或退回下一级只做局部补齐。

判级必须以产出证据为准。角色名称、Prompt 自述或用户指定的头衔，都不能直接证明实际 Level。
